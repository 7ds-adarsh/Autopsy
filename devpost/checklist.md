  PRD ref: `prd.md → Screen 1 — Landing Page`, `prd.md → Screen 2 — First-Time Dashboard`, `prd.md → GitHub Authentication`
  Spec ref: `spec.md → Stack`, `spec.md → Custom Server`, `spec.md → GitHub Integration`, `spec.md → Database Client`, `spec.md → File Structure`
  Build: Scaffold Next.js 16 + TypeScript + Tailwind + shadcn/ui. Create server.ts (custom server with Next.js + Socket.IO stub — no events yet). Set up PostgreSQL + Drizzle (schema for users table, first migration). Configure Auth.js with GitHub OAuth provider. Build shell layout (sidebar with Dashboard / APIs / Incidents / Repositories / Settings, GitHub avatar at bottom). First-time dashboard state (greeting, "Connect Repository" CTA, 01–04 setup progress indicator showing 01 current). Minimal landing page ("API AUTOPSY" header with Login and Get Started links, hero headline, primary "Connect GitHub" CTA, basic flow description — functional and navigable, not visually polished; full forensic dark-mode identity is Slice 6).
  Verify (mechanical): `npm run dev` starts without errors on Node 20.9+. Visit `http://localhost:3000` — landing page loads. Click "Connect GitHub" — OAuth flow completes and redirects to the dashboard shell. Check the database: `users` table contains one record with `githubId`, `username`, and `avatarUrl`.   Learner check: Open the app, click "Connect GitHub", complete the flow, and confirm you land on the dashboard shell. Does the sidebar show the correct navigation items with your GitHub avatar at the bottom?

- [ ] **2. GitHub App installation + repository scanning + API candidates**
  Becomes usable: From the dashboard, you can install the GitHub App on a repository, trigger a scan, and see a list of discovered API candidates with their file location, evidence snippet, and confidence level.
  Why now: Repository intelligence is the unique kernel of this product. Proving the scanner can actually read code and find real API usage patterns is the most important technical risk. If the GitHub App integration is broken or the pattern matching produces nothing useful, we need to know now — not after the whole UI is built.
  PRD ref: `prd.md → Screen 3 — Repository Scan`, `prd.md → Repository Connection and Scan`
  Spec ref: `spec.md → GitHub Integration`, `spec.md → Repository Scanner`, `spec.md → API Routes` (`/api/github/app/callback`, `/api/repositories`, `/api/repositories/[id]/scan`)
  Build: Set up Octokit GitHub App client (`lib/github/app.ts`) with installation token generation. Build GitHub App installation callback route (`/api/github/app/callback`) — receives `installation_id`, fetches repo metadata, stores in `repositories` table. Build repository list API route. Build scanner (`lib/scanner/index.ts`): fetch file tree recursively, apply ignore filters (node_modules, .git, dist, build, .next, coverage, vendor, lockfiles, binaries), fetch source file contents, run regex patterns (`lib/scanner/patterns.ts`) to find HTTP calls, base URLs, endpoint paths, and response field references. Build `/api/repositories/[id]/scan` route. Build "Connect Repository" UI: GitHub App install redirect button, installation callback handling, repository record display, scan trigger. API candidates list component (file, line, evidence, confidence badge, "Add Monitor" button). Setup progress indicator updates to step 01 ✓ / 02 current.
  Verify (mechanical): Install the GitHub App on the demo fixture repository. Call `POST /api/repositories/[id]/scan`. Confirm response includes at least one candidate with `endpoint`, `file`, `line`, `evidence`, and `confidence` fields. Verify `node_modules` and `dist` paths are not in any candidate's `file` field. Confirm `repositories` table has the repository record with `installationId`.
  Learner check: Connect the fixture repository, wait for the scan, and confirm you see the `payment.customer_id` reference discovered as a candidate. Does the evidence snippet look like what you'd expect from the code?
  Commit: `GitHub App integration and repository scanner with API candidate discovery`

  Why now: This completes the setup path and creates the baseline that everything downstream depends on. Credential encryption must be proven correct before any real credentials are stored.
  PRD ref: `prd.md → Screen 4 — Configure Endpoint`, `prd.md → Screen 5 — Establish Baseline`, `prd.md → Endpoint Configuration`, `prd.md → Baseline`
  Spec ref: `spec.md → Credential Encryption`, `spec.md → HTTP Client`, `spec.md → API Routes` (`/api/monitors`, `/api/monitors/[id]/test`, `/api/monitors/[id]/baseline`)
  Build: Implement `lib/crypto/credentials.ts` (AES-256-GCM encrypt/decrypt using Node crypto). Create `api_monitors` and `api_credentials` tables in Drizzle schema + migration. Build `/api/monitors` (create), `/api/monitors/[id]/test` (test connection — classify success / auth-error / transport-error / server-error; decrypt credentials server-side only), `/api/monitors/[id]/baseline` (capture live or sample). Endpoint config page: pre-fill from discovered candidate, API Details section, Request Configuration section (path/query params, headers), Authentication section (None / API Key / Bearer Token — credential entered once, never shown after save). Test Connection result display. Baseline page: "Capture Current Response" and "Use Sample JSON" paths, JSON viewer, structural summary table, "Use This as Baseline" confirmation. Setup progress 02 ✓ / 03 current / 04 pending.
  Verify (mechanical): Create a monitor with an API key credential. Confirm `api_credentials` table stores an encrypted value (not plaintext). Confirm `/api/monitors/[id]/test` returns success for a valid endpoint and `auth-error` for a wrong key — and that neither response contains the credential value. Confirm baseline is saved with `responseBody` and `structureSummary` in the `baselines` table.
  Learner check: Configure the payment endpoint with a credential, test it, and establish a baseline using the sample JSON path. Inspect the database — can you confirm the stored credential is encrypted (not the raw value you typed)?
  Commit: `Endpoint config, credential encryption, test connection, and baseline capture`

- [ ] **4. The kernel: diff engine + incident pipeline + Gemini Autopsy (both paths)**
  Becomes usable: The deterministic diff engine is unit-tested. Both the real-check path and the simulation path run the same `runIncidentPipeline()` — the only difference is the response source and `isSimulation` flag. Triggering either path via API route produces an incident record and a complete Autopsy Report in the database.
  Why now: This is the unique kernel of API Autopsy. Proving both paths converge correctly — and that error classification, security boundaries, and Gemini failure handling all work — before building any real-time UI means the demo backend is verified independently.
  PRD ref: `prd.md → Incident Pipeline`, `prd.md → Autopsy Report`, `prd.md → Simulate API Change`, `prd.md → States and Boundaries`
  Spec ref: `spec.md → Schema Diff Engine`, `spec.md → Monitor Executor`, `spec.md → Incident Pipeline`, `spec.md → Repository Impact Analyzer`, `spec.md → AI Provider`, `spec.md → Socket.IO Server`, `spec.md → Important Failure Modes`
  Build: Implement `lib/diff/schema-diff.ts` — pure recursive JSON structural diff returning `DiffResult` with `FieldChange[]`. Add Vitest unit tests covering: field removed (breaking), field added (additive), type changed (breaking), nested field renamed, property ordering ignored, no changes returns `hasChanges: false`. Implement `lib/impact/repository-impact.ts` — search cached repo files for references to changed field paths (dot notation, bracket, destructuring). Create `incidents` and `autopsy_reports` tables in Drizzle schema + migration. Implement `lib/ai/provider.ts` (AIProvider interface + types), `lib/ai/gemini.ts` (GeminiProvider: model from `GEMINI_MODEL` env var, structured prompt with only `AutopsyInput`, JSON response parsed to `AutopsyReport`, credentials excluded from context, Gemini failure saves incident but marks report as `failed` — does not lose the incident). Implement `lib/pipeline/incident-pipeline.ts` — shared pipeline used by both paths: normalize → load baseline → diff → if no changes exit cleanly → classify severity → create incident → emit `incident:created` → repository impact → emit `autopsy:started` → call AIProvider → save autopsy report (or mark `failed` on Gemini error) → emit `autopsy:completed`. Implement `lib/monitor/executor.ts`: `executeMonitorCheck()` classifies HTTP responses — 200 → pipeline; 401/403 → auth-error (log, update `lastStatus: error`, no incident); 5xx/timeout/DNS → transport-error (log, update `lastStatus: error`, no incident). `executeSimulation()` takes fixture JSON, skips HTTP call, runs same pipeline with `isSimulation: true`. Build `/api/monitors/[id]/check` and `/api/monitors/[id]/simulate` routes.
  Verify (mechanical): `npx vitest` — all diff unit tests pass. **Real path:** call `POST /api/monitors/[id]/check` against the configured endpoint — confirm `lastCheckedAt` updated, no incident created (response unchanged). Manually modify the baseline to simulate a change → call `/check` again → confirm incident created with `isSimulation: false`. **Simulation path:** call `POST /api/monitors/[id]/simulate` with canonical fixture (customer_id removed, customer.id added) → confirm incident with `isSimulation: true`, `severity: critical`, and autopsy report with `proposedPatch` and `confidenceEvidence` in the database. **Error paths:** send a request to a URL returning 401 — confirm no incident in DB and `lastStatus: error`. Send to a non-existent host — confirm same. Send an unchanged response — confirm no incident. **Security:** grep the autopsy_reports table and the server logs for any credential value — confirm absent. Confirm Socket.IO events `incident:created`, `autopsy:started`, `autopsy:completed` appear in server console for the simulation path.
  Learner check: Trigger the simulation via the API route and inspect the database. Is the `proposedPatch` correct (`payment.customer_id` → `payment.customer.id`)? Is the credential absent from the report? Does the real-check path classify a 401 correctly — no incident in the DB?
  Commit: `Core kernel: diff engine, dual-path incident pipeline, Gemini autopsy, error classification`
